## The problem

A lot of recommendation work stalls between the notebook and production. The prototype shows a lift offline, then someone has to rebuild it for live traffic, inside a latency budget, on data that changes with every play, and with rules about what must never be shown. I wanted to do both halves on public data so the tradeoffs are out in the open.

The data is the UCSD Steam dataset, with 52,857 players, 5,329 games and 3.15 million plays. I kept players with at least 10 games and games with at least 20 players.

## Stage one, the research prototype

Two retrievers each pick 100 candidates. A learned ranker then reorders the union, which is about 157 games per player.

| Model | NDCG@10 | Recall@10 | Coverage@10 |
|---|---|---|---|
| Popularity | 0.222 | 0.203 | 0.8% |
| Item kNN (cosine, top 100 neighbours) | 0.266 | 0.248 | 4.6% |
| PureSVD (64 factors) | 0.184 | 0.172 | 6.4% |
| **Two stage, kNN and SVD then LightGBM LambdaRank** | **0.327** | **0.311** | **10.8%** |

*Measured on 5,000 players whose held out games the models never saw.*

- The ranker beats the best single model by **23% on NDCG@10** and recommends from **2.3 times** as much of the catalogue.
- Popularity is a strong baseline, but it only ever shows 0.8% of the catalogue. You miss that echo chamber if you only track accuracy.
- Retrieval finds 67% of the held out games for each player, and the ranker can never do better than that. The next gain is in retrieval, not ranking.

One caveat. The dataset has no timestamps, so the test set is a random 20% of the games for each player rather than the latest ones. That makes the offline numbers optimistic, and a real launch would be decided by an online test.

## Stage two, the production service

<ArchDiagram />

- **Real time by design.** Both retrievers score from play history alone. The SVD user vector is just a weighted sum of item vectors, and kNN adds up neighbour lists. So a play changes the next response with no retraining and no model to update per player.
- **The ranker runs in plain TypeScript.** I load the 300 trees from the LightGBM JSON dump into flat typed arrays. There are no native dependencies, which keeps the serverless bundle small.
- **Parity is a test, not a hope.** A fixture from the Python prototype checks that the service gives the same candidates, all 12 features and the same ranker scores for 25 players.
- **Every pick explains itself.** The response names the game the player played that links most strongly to each pick, like "players of Civilization V also play this". If nothing links, it falls back to the closest game in the embedding space.
- **Guardrails come first.** Every response lists the rules that fired.
  - **Cooldown.** After 20 plays or 180 minutes in an hour, it shows nothing and suggests a break.
  - **Exclusions.** A global blocklist, plus any games or genres the player has excluded.
  - **Diversity.** No more than 4 games from one genre in a response.
  - **Cold start.** Popular games, still filtered.

## Latency

| Stage | p50 | p99 |
|---|---|---|
| Retrieval over 5,329 games | 0.93 ms | 1.24 ms |
| Ranking, 300 trees over about 157 candidates | 2.21 ms | 2.54 ms |
| Guardrails and explanations | 0.09 ms | 0.51 ms |
| **Total inside the service** | **3.24 ms** | **3.87 ms** |

The work is all CPU, and that decides how it gets deployed. One Node process handles about 320 requests a second. With one request at a time, p99 over HTTP is 4.3 ms. With 8 at once it is 40 ms, and with 32 it is 164 ms, and all of that extra time is queueing. So you meet the budget by giving each request its own instance, or running a process per core, not by making one process faster.
